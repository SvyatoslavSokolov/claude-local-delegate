# HARNESS_ARCHITECTURE.md
# Обязательный стандарт оркестрации и паттерны делегирования

> **Статус документа:** Нормативный стандарт проекта `claude-local-delegate`.  
> Все создаваемые задачи, инструменты и дочерние агенты **ОБЯЗАНЫ** следовать описанным ниже архитектурным паттернам. Запрещается реализовывать схемы взаимодействия, нарушающие эти правила.

---

## 1. Фундаментальный принцип: Детерминизм против «Сломанного телефона»

Исследования мультиагентных систем (SWE-bench, LMSYS, Princeton SWE-agent) доказали:
- **Антипаттерн «Свободный агентский чат» (CrewAI/AutoGen):** Передача неструктурированных инструкций между агентами на естественном языке приводит к экспоненциальному накоплению ошибок (*Telephone Game*), потере 20–30% контекста на каждом переходе и бесконтрольному сжиганию токенов ($O(N^2)$).
- **Стандарт нашего Harness:** Агенты взаимодействуют **ИСКЛЮЧИТЕЛЬНО** через:
  1. **Строгие структурированные контракты** (JSON-задачи в `coordination.sqlite3` с точными путями файлов);
  2. **Артефакты на диске** (`git diff`, изменённые файлы, сохранённые логи);
  3. **Детерминированные оракулы** (прогон `pytest`, линтеров, компиляторов через Bash).

Ни один промежуточный агент не имеет права передавать задачу дальше в виде вольного текстового рассуждения.

## 3. Четыре обязательных архитектурных паттерна

### Паттерн 1: «Architect + Editor» (Контрактное редактирование)
* Верхнеуровневая модель (Opus или Google) **НЕ выполняет построчное редактирование**. Она формирует строгую спецификацию:
  - Точный путь к файлу;
  - Анкоры строк (`:LINE`) и сигнатуры;
  - Требуемый контракт изменений.
* Локальный воркер (Qwen на 4x 3090) получает эту спецификацию и физически вносит изменения через инструменты `Edit`/`Write`.

### Паттерн 2: «Worker + Deterministic Oracle Loop» (`delegate_verified`)
* Никакой код не считается принятым на основе «уверенности» языковой модели.
* Валидация выполняется **детерминированным оракулом**:
  1. Воркер вносит правку;
  2. Запускается чекер (`pytest`, `mypy`, `py_compile` с проверкой скоупов);
  3. Если тест красный — воркер итеративно исправляет ошибку (до `max_iters`, по умолчанию 3);
  4. Супервизор получает управление **только когда тесты зелёные** или исчерпан лимит попыток.
* Супервизор не тратит платные токены на чтение промежуточных стектрейсов ошибок.

### Паттерн 3: «Fan-out 8x с Ground-Truth отбором» (`fan_out_to_local`)
* Рутинные задачи (покрытие тестами, аудит модулей, типизация) распараллеливаются на свободные слоты vLLM (до 8 одновременных агентов).
* При решении сложных алгоритмических задач допускается *Best-of-N sampling*: параллельный запуск с разными `temperature`. Вариант, первым прошедший верификацию тестами, принимается; остальные сессии останавливаются (`stop_delegate`).

### Паттерн 4: «Context Condenser» (Локальная компрессия контекста)
* Запрещено загружать в контекст Opus сырые логи сборки, дампы трассировок или 50 файлов проекта.
* Локальная Qwen 27B с окном 264k локально сжимает информацию:
  - Вырезает AST и интерфейсы;
  - Находит 20 строк первопричины ошибки;
  - Передаёт супервизору выжимку размером < 2k токенов.

## 4. Правила оформления задач (Task Briefing Guardrails)

Каждая задача, передаваемая через `delegate_to_local` или `delegate_to_agy`, обязана соблюдать правила из [TASK_DESIGN.md](TASK_DESIGN.md):

1. **Consumer Discovery — предварительное условие (Gate):**  
   Поиск зависимостей и вызовов удаляемого/изменяемого кода выполняется **ДО** любых правок. Если найдены живые потребители — агент обязан остановиться и доложить.
2. **Один файл на воркера:**  
   Запрещено поручать воркеру массовую правку нескольких крупных файлов в одной сессии. Задача делится на атомарные шаги по 1 файлу с указанием точных строк-анкоров.
3. **Строгая изоляция и предварительное резервирование:**  
   Перед запуском пишущего воркера обязателен вызов `task_claim` с указанием конкретных путей (`paths`), чтобы исключить коллизии между параллельными воркерами.
4. **Конкретный оракул и контрпример:**  
   Критерий приёмки должен содержать точную команду проверки (например, `pytest tests/test_auth.py -k test_jwt`) и требование показать вывод команды.

## 5. Единая точка наблюдения (Single Pane of Glass)

Вся иерархия оркестрации фиксируется в локальной базе и доступна через единый интерфейс:
* База задач и блокировок: `~/.claude-local-delegate/coordination.sqlite3`
* Метаданные локальных воркеров: `~/.claude-local-delegate/runs.json`
* Метаданные Google-агентов: `~/.claude-local-delegate/agy_runs/`
* Монитор иерархии в реальном времени:  
  ```bash
  python3 tree_monitor.py --watch
  ```
  Отображает дерево: *Проект $\to$ Супервизор $\to$ Задачи $\to$ Архитекторы $\to$ Воркеры на 3090*, статус каждого агента, используемую модель и загрузку слотов кластера.
